# Architecture

PAYRAKSHA 360 is **one Python process that serves three single-page apps and one shared API**. This document explains how the parts fit together and why they were built this way.

> DEMO / SIMULATION: no component talks to a real bank, UPI network or payment gateway.

## 1. Components

│   /api/bank/*   vendors, payments, AI audits, settings                         (bank/)      │

## 2. Data flow of one phone check

1. **RakshaPay** decodes a QR (camera via `jsqr`, gallery image, sample, or the console's target QR).
2. It calls `POST /api/link/scan` with `{device, source, input}`, with a 2.5-second timeout.
3. The backend runs `engine.analyze(input)` and returns a **RiskReport**, plus an optional ML insight. It also appends a **LinkEvent** to the in-memory link store (a deque of 50, guarded by a lock).
4. If the backend is unreachable, the phone runs the **same engine in JavaScript** (`shared/reference/engine.mjs`) and the check still works offline.
5. The **console** polls `GET /api/link/events?after=<seq>` every second. New events raise a toast, update the Device Link mirror and become the "current case" for the Explanation, Scam DNA and Attack Chain pages.
6. The user's choice (`cancelled`, `verify`, `trusted`, `paid_demo`) is sent with `POST /api/link/decision`. Context chips re-check the payment with `replaces`, so the event is updated in place.

## 3. Key design decisions

| Decision | Why |
|---|---|
| **Deterministic, weighted engine, not a black-box model** | The score must be explainable to a customer in one sentence and auditable by a bank. Every point in the score is a `Contribution` with a label and a reason. |
| **One engine spec, two runtimes** | The phone must work when the server is down. `engine.mjs` is the executable spec; `engine.py` is a port. `shared/golden/golden.json` (103 cases) is generated by the JS engine and replayed by the Python tests, so the two cannot drift apart. |
| **All tunables in `shared/*.json`** | Weights, thresholds, lexicons and combination bonuses can be changed without touching code, and both runtimes pick them up. |
| **ML only as a second opinion** | The TF-IDF model is trained on a small synthetic corpus and is shown separately. It never changes the explainable score. |
| **Link store in memory** | The live link is a demo channel, not a ledger. Nothing is persisted, so a restart gives a clean demo. |
| **Three ports, one process** | Each app keeps its own origin (the phone app needs its own HTTPS address for the camera), but they share one link store and one database without any extra services. |
| **Every external dependency has an offline fallback** | Postgres → SQLite; OmniRoute AI → simulated auditor; OSM street tiles → offline SVG map of India; backend → JS engine. The demo never breaks on bad Wi-Fi. |
| **Safety enforced in code, not only UI text** | Non-`@demo` UPI IDs are masked and analysis-only; decoded QRs open a check screen, never a payment; no input anywhere accepts a PIN, OTP, password or card number. |

## 4. Ports and processes

| Mode | Console | RakshaPay | Auditor | API |
|---|---|---|---|---|
| Exe / launcher | 7480 | 7481 | 7482 | same ports |
| `npm run dev:all` | 5173 (Vite) | 5174 (Vite) | `npm run dev:auditor` | 8000 (uvicorn, proxied as `/api`) |

The launcher (`packaging/launcher.py`) picks the app to open from the exe name (`1-Bank-Console`, `2-RakshaPay`, `3-AI-Auditor`). If the server is already running, it only opens the browser.
