# Risk engine

The engine answers one question **before** a payment: *does this payment situation make sense?* It is deterministic and explainable: every point of the score comes from a named signal with a plain-language reason.

* Executable spec: [`shared/reference/engine.mjs`](../shared/reference/engine.mjs) (types in `engine.d.mts`)
* Python port: [`backend/app/engine.py`](../backend/app/engine.py)
* Configuration: [`shared/engine-config.json`](../shared/engine-config.json), [`lexicon.json`](../shared/lexicon.json), [`patterns.json`](../shared/patterns.json), [`url-rules.json`](../shared/url-rules.json), [`recipients.json`](../shared/recipients.json)
* Parity: [`shared/golden/golden.json`](../shared/golden/golden.json), 103 cases generated by the JS engine and replayed against the Python port

> All weights, examples and statistics are **SIMULATED HACKATHON DATA**, chosen for the demo rather than learned from real fraud records.

## 1. Input

```ts
interface AnalyzeInput {
  message?: string;      // SMS / WhatsApp / email text
  url?: string;          // a link to check (never fetched)
  qrText?: string;       // raw QR payload, e.g. upi://pay?pa=x@demo&pn=Name&am=499
  payment?: {            // optional context; missing fields are inferred from message / QR
    recipient?: string; amount?: number; merchant?: string; source?: SourceId;
    recipientVerified?: boolean; previousPayments?: number; typicalAmount?: number;
    urgency?: 'none'|'low'|'medium'|'high'; hasPaymentRequest?: boolean;
  };
  behaviour?: { onCall?: boolean; screenShare?: boolean; newDevice?: boolean; lateNight?: boolean; rapidAttempts?: boolean };
}
```

## 2. Pipeline

1. **Text analysis.** The message, QR merchant name and QR note are matched against the lexicon cue groups: `urgency`, `threat`, `authority`, `paymentRequest`, `lure`, `secrecy` and `credential`. The text is classified into a scam **category** (utility, bank KYC, customer care, shopping, prize, job, investment, refund, parcel, "receive money" QR, personal, unknown).
2. **URL analysis.** Look-alike brands, risky TLDs, IP-address hosts, `@` tricks, shorteners, excessive subdomains and misleading paths. No network request is ever made.
3. **QR analysis.** Parses `upi://pay` and the demo `PAYRAKSHA://demo-payment` payloads, and flags non-payment QRs, "scan to receive" wording and redirection.
4. **Payment context.** Merges the explicit payment fields with what was inferred: is the recipient in the directory, verified, previously paid? Is the amount unusual for this category?
5. **Features.** Ten factors, each normalised to 0–1 with a reason string.
6. **Scoring.** Weighted sum plus combination bonuses, clamped to 0–100.
7. **Explanation.** Level, Scam DNA strands, detected patterns, the attack chain, the top reasons, the adversary's likely next move and a recommendation.

## 3. Formula

```
points(factor) = round(weight × value)          value ∈ [0, 1]
score          = clamp(0, 100, baseline + Σ points(factor) + Σ combo.points)
```

Baseline = **12** (every payment carries a small residual risk).

| Factor | Weight | Raised by |
|---|---|---|
| `recipientNovelty` | 16 | Never paid this payee before; payee not in the directory |
| `urgency` | 15 | "today", "within 2 hours", "last chance", an urgent QR note |
| `behaviouralAnomaly` | 14 | On a call with the requester, screen sharing, new device, late night, rapid attempts |
| `impersonation` | 12 | Claims to be a bank / electricity board / courier, but the payee is not verified |
| `suspiciousURL` | 10 | Look-alike domain, risky TLD, IP host, shortener |
| `amountAnomaly` | 8 | Amount far above what is typical for the category or this user |
| `socialEngineering` | 8 | Threats, lures (prize, job, refund), secrecy, credential requests |
| `contextMismatch` | 8 | The story does not match the payment (e.g. a "refund" that needs you to pay) |
| `qrRedirection` | 6 | The QR redirects, is not a payment, or asks you to "scan to receive" |
| `untrustedSource` | 3 | Arrived via an unknown website, social media, WhatsApp or SMS instead of an official app |

### Combination bonuses (`shared/patterns.json`)

Dangerous pairs are worth more than their parts:

| Combination | Bonus |
|---|---|
| "Receive Money" QR + payment | +20 |
| Refund + outgoing payment | +8 |
| Prize win + upfront fee | +8 |
| Job offer + registration fee | +8 |
| Courier hold + fee demand | +8 |
| Unrealistic offer + new domain | +8 |
| Guaranteed returns + secrecy | +8 |
| Remote access + payment request | +6 |
| Bank KYC + payment request | +6 |
| Urgency + QR + unknown recipient | +4 |
| Suspicious link + unverified payee | +3 |
| Pressure tactics + payment request | +2 |
| Fake customer care + payment request | +2 |

## 4. Levels and actions

| Level | Score | Wording | RakshaPay primary action |
|---|---|---|---|
| `LOW` | 0–29 | LOW RISK | Pay (demo) |
| `CAUTION` | 30–59 | CAUTION | Verify payee |
| `HIGH_CAUTION` | 60–79 | HIGH CAUTION | Cancel payment (paying needs a 3-second hold) |
| `HIGH` | 80–100 | HIGH RISK | Cancel payment (paying needs a 3-second hold) |

The engine never states certainty. Headlines use "Suspicious", "Potentially risky" and "Multiple warning signals detected".

## 5. Worked example

The **Electricity Disconnection** demo QR (from `shared/scenarios.json`):

```
PAYRAKSHA://demo-payment
recipient=unknown-electricity@demo
amount=1999
merchant=Electricity Board Demo
source=WhatsApp Demo
urgency=true
recipientVerified=false
```

These are the real engine outputs:

| Contribution | QR alone | + on a call | + on a call + screen share |
|---|---|---|---|
| Baseline residual risk | 12 | 12 | 12 |
| Unknown recipient | 16 | 16 | 16 |
| Impersonation | 12 | 12 | 12 |
| Urgency | 8 | 8 | 8 |
| QR redirection | 6 | 6 | 6 |
| Context mismatch | 6 | 6 | 6 |
| Amount anomaly | 4 | 4 | 4 |
| Untrusted source | 2 | 2 | 2 |
| Behavioural anomaly | — | 5 | 12 |
| Combo: Urgency + QR + Unknown Recipient | 4 | 4 | 4 |
| Combo: Remote Access + Payment Request | — | — | 6 |
| **Score** | **70 HIGH CAUTION** | **75 HIGH CAUTION** | **88 HIGH RISK** |

The verified demo merchant with ₹250 scores **18 → LOW RISK**.

| Field | Used by |

## 7. ML second opinion (optional)

`backend/app/ml.py` trains a TF-IDF + logistic-regression classifier at start-up on a small **synthetic** corpus built from the scenarios. Its probability is shown as a separate "ML second opinion" and **never** changes the explainable score. If scikit-learn is missing, the insight is simply omitted.
