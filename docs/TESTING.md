## Engine parity (golden tests)

`shared/golden/golden.json` holds 103 inputs and the exact reports that the JavaScript reference engine (`shared/reference/engine.mjs`) produces for them: scores, levels, contributions and patterns. It is generated by `node shared/reference/gen-golden.mjs`. `backend/tests/test_golden.py` replays every case through the Python engine and requires an identical result, so the browser fallback and the server can never disagree. After changing weights or lexicons, regenerate the file and re-run `npm run test:py`.

## Acceptance tests

`test/acceptance/` holds contract tests written **from the specification, before the implementation**. They had to fail against the stubs first, which proves they exercise the real code:

* `test_link_api.py`: the scan event is visible from both apps; decisions re-sequence the event; 404 and 422 cases; the 50-event cap.
* `pay-logic.test.ts`: payee masking, analysis-only mode for real UPI IDs, the primary action per level, and context chips re-scoring.
* `constellation`, `next-move`, `operation-timeline`, `payment-twin`, `scam-radar`, `soc-shell`: console visual components.

## Safety assertions

Several tests guard the safety rules directly:

* RakshaPay never renders a PIN, OTP, password, CVV or card input.
* A decoded QR routes to the check screen, never to a payment.
* Non-`@demo` recipients cannot be paid and are masked.
* Outcome screens always state that no money moved.

## Manual user test (done before release)

1. Log in with `3023`; a wrong code is rejected.
2. Electricity scam sample → 70 HIGH CAUTION → "on a call" → 75 → Cancel → "No money moved"; the console mirrors each step.
3. Verified merchant ₹250 → 18 LOW → Pay (demo) → wrong code rejected → `2026` → done.
4. Camera denied or silent → help card with Try again (no black screen).
5. No console errors in any app.
